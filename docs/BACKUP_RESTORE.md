# Backup and restore (Phase 10.5H)

## Scope and safety

The offline backup component in `rag_agent.api.backup` packages a consistent SQLite snapshot of the document registry and its managed tenant files. It keeps only the `documents` and `binding` tables; authentication users, password hashes, sessions, CSRF state, rate-limit state, credentials, and Qdrant vectors are excluded. The binding can contain the Qdrant URL and collection name, so the archive may reveal internal service topology even though credentials are excluded. Existing documents without a tenant assignment remain unassigned and are not made visible to a tenant by backup or restore.

The archive is **not encrypted**. It contains uploaded PDFs and parsed document JSON, which must be treated as sensitive data. Store it only on access-controlled encrypted media, or encrypt it with an independently approved tool before it leaves the host. The HMAC integrity key is supplied to the backup/restore caller, must be at least 32 bytes, must be stored separately from the archive, and is never included in the archive or manifest. Losing the key prevents integrity verification and restore.

The implementation refuses symlinked or unknown source entries, incomplete active document files, an active document writer, unsafe destinations, and existing backup/restore destinations. It writes to a private temporary file and publishes the completed backup without replacing an existing path. Restore validates the manifest HMAC, each listed file's size and SHA-256, archive membership, schema version, SQLite integrity, and tenant file references before publishing into a new directory.

## Quiescence and ordering

Stop the API and any other process using the document store before calling backup. `DocumentManager` holds the `writer.lock` for its lifetime, so backup intentionally refuses to run while a manager owns the store. This also prevents copying files while ingestion or deletion is changing the registry. Do not copy the database and files independently while the application is running.

Restore only to a new path whose parent already exists. The operation does not overwrite or merge an existing destination. It extracts and validates the archive in a private `.rag-restore-*` staging directory created under the destination parent, assembles the final SQLite/files layout there, and repeats SQLite, schema, tenant-ownership, and file-reference validation. It flushes staged files and directories where the platform supports it, then writes a completion marker only after validation. The final directory is published with one same-filesystem directory rename that refuses to replace an existing destination (`renameat2(RENAME_NOREPLACE)` on Linux; `os.rename` on Windows). Unsupported platforms fail closed. It does not restore authentication accounts or sessions; reprovision the owner through the approved local account procedure and treat all prior sessions as revoked.

On ordinary process exceptions and Python interrupts before publication, the context manager attempts to remove the staging directory and the destination remains absent. A hard process termination can leave `.rag-restore-*` behind. `list_restore_staging_directories(parent)` reports such directories without modifying them. A stage is eligible for operator inspection as fully assembled only when it contains `.restore-stage-ready`; publication checks that the marker has the expected fields, matches the active archive identifier and requested destination, and is a bounded regular file. The marker is written after validation, is not separately HMAC-signed, and is not a substitute for revalidating the data. Stages without the marker are incomplete. The helper deliberately does not delete stages: an operator must ensure no restore is active, inspect the stage, and handle sensitive contents under the site's retention procedure. A process termination immediately after publication leaves either no destination or the already assembled destination for the tested atomic-rename boundary; the destination must still be checked with the normal restore verification procedure before service use.

Atomic rename provides a namespace-level publication boundary on supported same-filesystem implementations; it does not alone guarantee persistence across sudden power loss. On POSIX, the implementation fsyncs staged files and directories and attempts to fsync both rename parent directories. Windows file and directory fsync are skipped because the current portable file-descriptor implementation is not supported there; the rename still provides its platform's namespace operation, but no power-loss durability claim is made. Actual durability also depends on the filesystem, storage device, controller, and operating system. If parent-directory flushing fails after rename, restore reports that publication occurred but durability could not be confirmed; the complete destination is not rolled back. Use a reliable filesystem and retain the original backup until independent post-restore verification is complete.

## Qdrant and service recovery limitation

Qdrant snapshot capture, transfer, restore, and reconciliation are **not implemented** by this component. SQLite binding metadata can identify the collection that the registry was associated with, but the corresponding vectors are not present in this archive. A successful component restore is not a complete RAG service recovery and must not be exposed to users as a recovered service until a separately validated Qdrant snapshot restore or controlled re-index has reconciled vectors and document metadata.

A future coordinated recovery procedure must quiesce writes, capture a remote Qdrant snapshot for the exact collection, capture the registry/files backup from the same maintenance window, preserve both artifacts and their hashes, restore Qdrant first into a disposable/new target, restore registry/files to a new document directory, verify vector counts and tenant payloads against registry records, and only then enable the API. Failure must leave the old deployment untouched and the new target unpublished. Rollback must switch back to the preserved old deployment rather than overwrite it. This sequence is a design requirement only; it has not been implemented or tested against a remote Qdrant server.

## API use

The supported Python entry points are `create_backup(document_dir, destination, integrity_key=...)` and `restore_backup(archive_path, destination, integrity_key=...)` in `src/rag_agent/api/backup.py`. Paths must be absolute; the backup destination parent must already exist and be separate from the source. Keep the key in a protected operator secret store and pass it to the caller without logging it or placing it in the archive. No public HTTP endpoint or automatic production restore is provided.

The Phase 10.5H automated tests use synthetic SQLite databases, synthetic tenant files, temporary directories, and an in-memory Qdrant client only to verify restored tenant-scoped inventory. They do not establish remote Qdrant snapshot compatibility, full vector recovery, production restore readiness, or encryption at rest.
